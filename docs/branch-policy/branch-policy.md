# ブランチ運用とバックアップ方針

目的
- リポジトリの安定性を保ちながら効率的に共同作業するための最低限の運用ルールを定義します。

適用範囲
- `main` と `feature/`、`fix/`、`docs/`、`chore/` 系ブランチに対して適用します。リポジトリ運用担当はオーナー（`oggy8021`）とします。

ブランチ命名
- 機能追加: `feature/<短い説明>`
- バグ修正: `fix/<短い説明>`
- ドキュメント: `docs/<短い説明>`
- 雑務: `chore/<短い説明>`

PR とマージ
- 直接 `main` へ push せず、PR 経由で変更を取り込みます。
- CI（テスト・Lint 等）がグリーンになるまでマージ不可。
- マージ方式: 原則 `squash`（例外は合意のうえ）。
- 少なくとも 1 件のオーナー承認（レビュー）を推奨。

バックアップ（`save/` 等）と生成物
- `save/*` はバックアップ用パスとして PR チェック対象外とします。
- 一時的な生成レポート（例: `docs/*-report*.md`）は `.gitignore` に追加し、通常はコミットしない運用とします。

コンフリクト解消
- Web Editor 等でリモート上から直接コンフリクトを解消しないでください。
- コンフリクトはローカルで解消し、チャット内で合意を得てからコミット→push→PR の順で対応します。

ブランチライフサイクル
- 作業完了後はリモートの feature ブランチを削除しても良い（オプション）。長期保管が必要な場合は `archive/<name>` にリネームして保管します。

緊急対応（ホットフィックス）
- 緊急の修正は `fix/hotfix-YYYYMMDD-短い説明` のように命名し、最小限の変更で PR を作成、CI が通ったら速やかに `main` へマージします。

例外・変更管理
- 本方針の変更は Issue を起票し、オーナー承認のうえで `docs/` 内の方針ドキュメントを更新します。

問い合わせ先
- 運用に関する質問は Issue で立てるか、リポジトリオーナーに直接相談してください。

# ブランチ運用ポリシー（簡易）

目的: ブランチ運用の共通ルールを明示し、レビュー・CI の品質を担保する。

1.ブランチ命名
   - 機能: `feature/<短い説明>`
   - 修正: `fix/<短い説明>`
   - 雑務: `chore/<短い説明>`

2.ワークフロー
   - 機能ごとにブランチを作成し、実装→PR作成→レビュー→CI通過→`main` にマージ。
   - 小規模ドキュメントは `main` へ直接コミット可（合意済み）。
   
   [注記: 現在は `docs/` の一括整備を `feature/docs-consolidate-001` 上で進める方針です。`main` への直接コミットと運用が競合しないか確認してください。]

3.PR 要件
   - PR には必ず仕様書（`docs/specs/*.md`）へのリンクを含めること。
   - CI が緑（テスト・Lint）になるまでマージ不可。
   - 少なくとも1回のオーナー承認（レビュー）を要する。

4.マージ戦略
   - Squash マージを推奨。履歴をシンプルに保つ。チームで別戦略を使う場合はここを更新。

5.ブランチ保護（推奨設定）
   - `main` ブランチに対して以下を有効化することを推奨:
     - Force push 禁止
     - PR によるマージのみ許可
     - 必須のステータスチェック（CI）が成功すること
     - 必要に応じてコードオーナーやレビュワーの承認を必須にする

注: 実際のブランチ保護設定は GitHub リポジトリの管理画面または API から行ってください。
