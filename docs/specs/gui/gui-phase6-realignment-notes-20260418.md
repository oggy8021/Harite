## Add.1: Apply の "Single" 再点検

1. Apply は、Optimize 済みの結果を、OS の通常動作のまま plugin に委ねて貼り付ける操作を指す。
2. GUI にある "Single" は、CLI 側に存在する明示モード名ではなく、通常 Apply 経路を便宜的に名付けた internal label に近い。
3. 現在の CLI `apply` は通常 apply が単一ファイル経路であり、必要時だけ per-monitor 系の指定が追加される構造である。
4. よって GUI で "Single" を per-monitor の対概念として露出するのは不自然であり、Apply 自体が通常適用を表すと読む方が自然である。
5. per-monitor は、2 画面を意識してそのように Compose し、monitor ごとに貼りたいという追加要求を指す。
6. `--auto-split` は、さらに高い期待を伴う拡張であり、plugin 層が OS ごとの monitor 別貼り付けをラップできる場合に限って成立する。
7. CLI parity を厳密に取るなら、概念上は `default` / `per-monitor explicit` / `auto-split` の 3 分岐がある。
8. ただし現 GUI の `Open-L` / `Open-R` は optimize 前の素材入力であり、CLI の `--left-file` / `--right-file` のような apply 時の独立 target 指定とは同義ではない。
9. CLI の `per-monitor explicit` は、既に monitor ごとに分かれた出力ファイルを apply 段で明示指定する経路を指す。
10. 現 GUI には apply 段で左 monitor 用 / 右 monitor 用のファイルを個別指定する UI がないため、`per-monitor explicit` はまだ本当に選べる状態ではない。
11. さらにこの `per-monitor explicit` は、optimize と apply をコマンド分離し、apply 側に `--left-file` / `--right-file` を持たせた Harite CLI 上の convenience であり、母体プログラムの主要ユースケースとは限らない。
12. この系統の convenience は、既に `--do-it` を削った判断と同種に扱ってよい。つまり、母体根拠が薄く、Harite の中核価値を強めないものは既定導線から外す。
13. 特に `--left-file` / `--right-file` は、monitor ごとの個別ファイル指定だけで完結してしまい、Harite の合成処理を経る必然性を弱めるため、採用価値を強く再点検すべきである。
14. 極端には、`left-file` / `right-file` が主導線になるなら「Harite 自体が要るのか」という疑義まで生じうる。
15. そのため現時点の GUI が実際に提供できる apply 分岐は、通常 apply と auto-split の 2 つであり、3 分岐プルダウンをそのまま出すと未実装 capability だけでなく、母体非準拠かつ Harite の存在意義を弱める convenience を主機能のように見せる危険がある。
16. 逆に `--left-file` / `--right-file` を廃止するなら、`per-monitor explicit` は同時に消滅し、残る `per-monitor` の実質は `auto-split` だけになる。
17. その場合、GUI/CLI ともに `per-monitor = auto-split` と整理した方が読みやすく、母体追従の観点でも自然である。
18. もし GUI でも `per-monitor explicit` を選ばせるなら、apply 段で monitor 別ファイルをどう指定し、どの optimize 出力と結び付けるかに加えて、それが母体準拠の導線として妥当か、さらに Harite の中核価値を損ねないかも先に設計する必要がある。
19. 見直し対象は名称だけでなく、Apply 導線そのものとスクリーンショット理解も含む。

## 判断済み前提（補足反映後）

1. Compose の仕様、優先度、強さは母体プログラムで凍結済みであり、Harite 側で再設計する対象ではない。
2. Open-L / Open-R を上下左右の tgl 群が囲む旧 Glade 配置がゴールである。
3. 現在の Compose の崩れは、特に Top-L / Top-R / Bottom-L / Bottom-R の位置ずれとして認識する。
4. fixed は GUI 上で独立した選択項目として見せる必要はなく、Open-L / Open-R による自明配置として吸収されるのが自然である。
5. fixed は UI から消し、見えない内部既定動作として扱う。
6. action 導線の最終結論は急がず、周辺の意味配置を整備する中で決める。
7. watch や prefs が画面上でどの程度目立つかは主論点ではなく、まずは母体プログラムへの近しさを優先する。
8. プレビュー導入後は理解性が大きく改善する見込みであり、現状の一部の弱さは恒久問題とみなさない。
9. MainWindow はリサイズ可能であり、その追随方針は以下を前提とする。
   1. アイコンはスケールアイコンの仕様上限まで追随する。
   2. プレビューは大きい画面・高解像度画面ほど有用性が上がる。
   3. テキストはデスクトップ指定のフォントサイズに委ねる。
10. debug エリアは現時点では不要であり、独立した帯としては廃止する。
11. 問題通知や補助情報が必要な場合は、専用 debug 帯を復活させず status 側へ集約する。
12. これまでの一部仕様は、オーナー記憶の想起途中での暫定承認と、母体未読の言語モデルによる補完が重なって足し込まれた可能性がある。
13. したがって、母体根拠が弱く、実際に使うか不明な convenience 仕様は、既定で採用せず棚上げまたは撤去候補として扱う。

## 真の未解決点

1. Top-L / Top-R / Bottom-L / Bottom-R の崩れを、旧 Glade 対応の具体差分として明文化すること。
2. Open-L / Open-R を中心に、上下左右 tgl が囲む構造を実画面上で復元すること。
   1. Top-L / Bottom-L は Open-L に個別対応し、Top-R / Bottom-R は Open-R に個別対応する。
   2. Path 表示 L/R および Clear-L/R は十字構成の外へ退避してもよいが、L 側 / R 側の補助情報として分離を保つ。
3. Apply 自体を通常適用とみなし、auto-split を追加要求として扱う導線に改めるべきかを再点検すること。
4. コントロールの配置が長らく到達しないのは意図的な変更によるものなのか、centeringなどの指定不足による未達なのかを、Owner に追跡可能な形で都度明文化すること。

## 誤読しやすい禁止事項

1. 母体プログラムで凍結済みの Compose 仕様を、Harite 側で未確定論点として扱わないこと。
2. Open-L / Open-R と tgl 群の関係を「結びつきが弱い」と抽象化せず、旧 Glade 配置との差分として具体化すること。
3. fixed を GUI 上の追加価値として再導入しないこと。
4. watch や prefs の画面上の目立ち方を、Phase6 の本筋より優先する議論にしないこと。
5. プレビュー導入で改善する論点と、プレビューがなくても直すべき論点を混同しないこと。
6. 意図的変更と未達状態を曖昧にしたまま進めないこと。
7. 母体根拠が薄い convenience 仕様を、記憶補完や実装都合だけで既定仕様へ昇格させないこと。
