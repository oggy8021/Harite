# ポリシー導出ドキュメント

以下は、現在のテスト・スクリプト・ドキュメント群を導出するにあたって採用されたポリシーとその理由、意思決定の履歴です。

## 基本方針（要点）
- チャット中心の作業フロー: 変更はチャットで合意したうえで PR を作成する（working-tree は基本的に PR 前に確定しない）。
- レビュー前提: 自動化は「レビュー前提」で動くようにする。スクリプトは `--dry-run` と差分レポートを出し、出力を必ず確認してからコミットする。
- 保守的な置換: ドキュメント正規化は誤検出のリスクを最小化する。コードブロックやインラインコードはプレースホルダ化して置換対象外とする。
- 言語ベースの除外: 英文のみのファイルや翻訳対象外のファイルはファイル名レベルで除外する（`--skip-pattern` を用いる）。
- CI はフェイルファストで詳細ログを残す。重要な自動化変更はマルチプラットフォームで検証する。

## なぜこの方針か
- 自動置換はコンテンツに不可逆の変更を加えうるため、レビュー前提としないと誤修正のリスクが高い。
- コードブロックやテーブルなどの構造的要素は自然言語の置換と相性が悪く、誤変換を引き起こすため排除する。
- 言語判定をファイル名で行うことで、誤判定の運用コストを下げる（heuristic より deterministic）。

## 具体的な導出手順（実務）
1. ドキュメント正規化の要件をチャットで合意。置換ルールは最小限（句読点、列挙の全角化等）。
2. スクリプトを `--dry-run` モードで実装し、差分を unified-diff で出力。差分は PR に添付して人がレビューできるようにする。
3. スクリプトはコードブロック・インラインコード・表行・diff ヘッダを除外する。これを抽出→置換→復元のフローで実装。
4. 言語除外は `--skip-pattern`（glob）を用いる。デフォルトに `*.en.md` を設定。
5. CI は変更を検証。テストが通らなければマージしない（branch protection）。

## 運用ルール（チェックリスト）
- スクリプト変更時: ローカルで `--dry-run` を実行し diff を生成、レビューを経て `--apply`（実運用引数）で PR を作る。
- PR 作成時: 1) 目的 2) 置換ルール一覧 3) 影響ファイルのサマリ を PR 説明に含める。 
- マージ: squash-merge を推奨（履歴を簡潔にするため）。
